## R1 · P2：重试旧回复会丢弃未发送草稿

位置：`Sources/MoxChat/ChatController.swift:202–207`。

`send(retryOf:)` 与发送新消息共用清空草稿的分支。存储层在 retry 时使用旧 userMessage，忽略传入的 prompt，但控制器仍将当前 draft 清空。因此用户完成一轮、在输入框写好下一条消息、点击旧回复“重试”，草稿会消失；它既没有提交也没有保存。输入框和重试按钮允许该操作。

修复：明确区分发送新消息与重试的输入消费语义；只有真正消费当前草稿的新消息才能清空它。无需复制整条生成流程。

验收：控制器集成测试覆盖非空草稿下重试旧回复，确认请求仍使用原 userMessage，当前草稿保持原样；普通发送仍正确清空已消费草稿，异步准备期间新输入不被误清空。以上缺陷由确定的代码路径确认，本轮未能运行新增回归测试。

## R2 · P2：历史摘要操作会加载并重新处理整个聊天库

位置：`Sources/MoxPersistence/ConversationStore.swift:187–209`；`Sources/MoxChat/ChatController.swift:372–382`。

`list()` 无分页读取全部会话、全部 attempt，再逐条查询并解码用户/助手全文。每次 `reload()` 又为所有历史回复重新构建 TextSegments 并常驻内存。启动、新建、发送前后、选择上下文及删除都走这条路径。于是新建一个空会话也会处理所有不相关历史，内存和操作成本随整个库的正文增长，而非当前打开的对话；现有单次 1MiB 输出性能测试不能证明长期使用的历史读取有界。移到后台线程没有消除全库 IO、全文副本和工作量。

修复：将会话摘要列表与会话详情读取分开；详情按实际选中会话获取，对较长历史提供有界加载策略；流式期间只更新当前 attempt 的呈现缓存。仍保留完整持久内容，不通过删历史解决问题，不建设通用 ORM。

验收：多会话长历史夹具下，读取列表/新建会话不读取其他会话的正文；切换会话、分页/按需读取和未保存回复保留正确。记录代表性历史规模下的内存及交互耗时。本轮未测得具体卡顿阈值，本项针对源码中确定的全库全文读取与重建行为。

## R3 · P2：打开聊天库失败时丢失定位所需的错误元数据

位置：`Sources/MoxPersistence/ConversationStore.swift:125–139`；`Sources/MoxChat/ChatController.swift:384–406`。

`ModelContainer` 创建/打开和初始 fetch 失败会直接向上传递。`show` 将非 MoxError 统一变成 `storageFailed`，环形诊断只记录 `stage=app`；export 的顶层 errorCode 又只来自 live 请求，因此启动失败时通常为空。原始 NSError 的安全 domain/code、发生在打开还是恢复阶段等信息均没有被 Mox 记录。虽然 save() 已有脱敏 OSLog，这条打开失败路径没有同等处理。用户看到“请检查诊断”，导出却无法区分模型/schema 问题和权限/磁盘问题；不能依赖系统偶然输出的内部日志补足本项目的诊断契约。

修复：在拥有操作语义的存储边界记录 open/recover/fetch/save 阶段及允许公开的 NSError domain/code，并以稳定错误交给 UI；导出包含最近一次操作失败，而不只取 live 请求。复用现有脱敏原则，不导出任意 description、userInfo、路径或正文。

验收：注入至少两种不同 Cocoa/POSIX 打开失败，验证 UI 不崩溃/不删库，诊断能够区分阶段和安全错误码，同时敏感哨兵不出现在日志/导出。

## 同步整理建议

修复涉及的聊天状态宜使用明确枚举，避免在 UI/存储/控制器多处维护 pending、streaming、stopping 等字符串集合。存储当前还直接依赖 GenerateBody/WireMessage 并保存完整 HTTP 请求（重复祖先正文）；调整 R2 时应把持久化数据和请求组装的职责理清，协议 DTO 留在传输边界，避免以后协议变化牵动数据库表示。这些建议没有被计为新增、已复现的运行缺陷，也不要求搭建新的抽象框架。
